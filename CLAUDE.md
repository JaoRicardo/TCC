# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

TCC (capstone) project: registration and management system for a Catholic community's camps (**Acampamentos**) and events (**Eventos**) — "Acampamento São Miguel Arcanjo". Monorepo with two apps:

- `backend/` — CakePHP 5.3 JSON API (PHP ≥ 8.2, MySQL 8). The README there is just the stock Cake skeleton README.
- `front-acamp/` — SvelteKit 2 + Svelte 5 (runes forced on for all project files in `svelte.config.js`) + TypeScript. README is the stock `sv` template.
- `Desing/` (sic) — Claude Design handoffs (prototypes + README with color/type tokens). Gitignored; reference only, not part of the app.

Code, identifiers, UI text, comments and commit messages are in **Portuguese**. Keep new code that way.

Runs on Windows 11 (the app is only ever run locally for the TCC presentation — no deploy, no cron/scheduler).

## Commands

Backend (run from `backend/`):

```sh
composer servidor                          # dev server on localhost:8765 with 6 MB uploads (plain php -S has 2 MB)
php vendor/bin/phpunit                     # full test suite
php vendor/bin/phpunit tests/TestCase/Regras/SorteioServosTest.php          # one file
php vendor/bin/phpunit --filter nomeDoTeste tests/TestCase/Regras/X.php     # one test
composer cs-check                          # phpcs (CakePHP standard); composer cs-fix to auto-fix
php bin/cake.php migrations migrate        # on Windows use bin/cake.php — bin/cake is a shell script
php bin/cake.php migrations seed
php bin/cake.php executar_prazos_formulario    # CAUTION: really disqualifies people past deadlines
```

Frontend (run from `front-acamp/`):

```sh
npm run dev                  # port 5173; Vite proxies /api and /uploads to localhost:8765 (vite.config.ts)
npm run dev:rede             # same, open to other devices on the LAN (http://<this PC's IP>:5173)
npm run check                # svelte-check (type checking) — the only static check; there is no linter or JS test suite
npm run build
```

Config/secrets live in `backend/config/.env` (DB, JWT secret, Mercado Pago) and `front-acamp/.env`; neither is in git. **Never run commands that put the DB password on the command line** (e.g. `mysql -pSECRET`). To inspect the DB, write a throwaway PHP script in the scratchpad that requires `vendor/autoload.php` + `config/bootstrap.php` and uses `ConnectionManager::get('default')`; wrap experiments in `begin()`/`rollback()`.

### Tests

- Tests run against a real MySQL database: connection `test` in `config/app_local.php` reuses the `DATABASE_*` vars with `DATABASE_TEST_NAME` (default `<DATABASE_NAME>_test`). `tests/bootstrap.php` aborts if the test DB equals the app DB, runs all migrations via `Migrator`, then clears the `_cake_model_` schema cache.
- The real tests are in `tests/TestCase/Regras/` and extend `RegrasTestCase` (transaction per test; factories `criarUsuario(admin: true)` = all permissions, `criarAcampamento`, `inscrever`, `jaFoiCampista`, `criarPergunta`, `autenticarComo`, `respostaJson`). Each business rule has a test file there — add/extend one when changing a rule.
- In `IntegrationTestTrait`, only the request *headers* are cleared after each request: call `autenticarComo()` again before every `get`/`post`. Other `configRequest` keys accumulate (`array_merge_recursive`) — for uploads, `unset($this->_request['files'])` before each `configRequest(['files' => …])` (see `DocumentoIdentidadeTest`).
- Mercado Pago is mocked with `Client::addMockResponse` (see `PagamentoTest`).

## Backend architecture

- **Routing**: every API endpoint is declared explicitly in `config/routes.php` under prefix `Api/V1` → `src/Controller/Api/V1/*`. There are no fallback routes for the API — new endpoints need a route line. `src/Controller/Api/AuthController.php` (no V1) is **dead code**; the real login is `Api/V1/AuthController`. Check the route before editing a controller.
- **Auth**: `JwtAuthMiddleware` decodes `Authorization: Bearer <token>` (access tokens only, non-deleted users) and sets the `identity` request attribute. CSRF is skipped for `/api/*`; CORS is a permissive inline middleware in `Application.php`.
- **`ApiController`** (base of all V1 controllers): `apiResponse()`/`apiError()` write raw JSON; `requireIdentity()` and `requirePermissao('<chave>')` return either the user or an error `Response`, so the idiom is:
  ```php
  $identity = $this->requirePermissao('setores');
  if ($identity instanceof Response) return $identity;
  ```
  `serializeUser()` is the single source of the logged-in user payload (login, register, `/users/me`, `/auth/me`) — including `permissoes`.
- **Permissions**: the `user_permissions` table is the *only* access rule (`users.is_admin`/`is_counselor` were dropped). Screen keys and dependencies live in `PermissoesService::TELAS`/`AREAS`; anyone with ≥1 screen enters the admin panel. Team roles inside an activity (servo geral / líder de setor / servo comum) are a separate, per-activity mechanism in `ActivitiesController` (`activities_general_servants`, `is_coordinator`).
- **Services** (`src/Service/`) hold the heavy business logic; controllers are thin wrappers: `SorteioService` (campista/servo raffles), `PrazoFormularioService` (form/payment deadlines, open slots, "chamar próximo"), `PagamentoService` (manual payments, see below), `MercadoPagoService` (Checkout Pro; **no longer used** — user decision 2026-11-21; kept switched off, its `prazoPagamento`/`valorDaTaxa` helpers are still used), `PermissoesService`, `JwtService`, `TravaExecucao` (MySQL `GET_LOCK` wrapper).
- **Sorteio só manual** (user decision 2026-11-22, handoff `Desing/design_handoff_painel_acampamento`): there is no automatic raffle any more; the organization raffles in Inscritos e Sorteios (`SorteioController`). The camp's raffle dates are only the *predicted* dates. When a raffle is done is stored in `campings.camper_raffle_done_at`/`servant_raffle_done_at` (cleared on reset; `SorteioService::sorteioFeitoEm`; older raffles count as done without a date). "Aguardando sorteio" and "Não sorteado" depend on the raffle being done, never on the date. `*_raffle_auto_ran_at` columns are leftovers.
- **Lazy-cron**: deadline sweeps (form, payment, correction) run opportunistically at the top of `ActivitiesController::index`, `SorteioController::resultado` and several `InscricoesController` actions (guarded by `TravaExecucao`). Consequence: simply hitting `GET /activities` or `/me/inscricoes` can mutate the dev DB — intercept those in browser tests when a deadline is near.
- **Pagamento manual** (handoff `Desing/design_handoff_painel_evento`, user decision 2026-11-21): no online payment and no payment link any more — the person pays the organization directly (dinheiro/Pix) and someone with permission `inscricoes` registers it in Inscritos e Sorteios › Pagamentos (`POST`/`DELETE /admin/inscricoes/{id}/pagamento`, `PagamentosController::registrar`/`desfazer`). `is_fee_paid` is still "paid"; `fee_paid_on`, `fee_payment_method`, `fee_registered_by/at`, `fee_note` say how. `PagamentoService` holds the rules: "precisa pagar" = camp titular with form sent / event inscription concluded; "Marcar como pago" works for any active inscription of a paid activity (paying early); whoever must pay and has no payment loses the vacancy **2 days after the deadline** (`DIAS_DE_FOLGA`), camps *and* events (sweep in `PrazoFormularioService::processarPagamentos`, logged as "Sistema" in the ficha). Undoing past the grace removes the vacancy at once. Lists carry `pagamento` = `PagamentoService::resumo`.
- **File questions** (question type `arquivo`, e.g. the "Documento de identidade" every form got at the top of its first section): the file uploads as soon as it's picked (`POST /inscricoes/{id}/arquivo` with `question_id`, `InscricoesController::enviarArquivo`) into `user_documents` (linked to `pre_registration_id` + `question_id`); the answer stores the file id, and on submit the server always uses the question's current file. Asked again on every inscrição. Files live in `backend/storage/documentos/` — outside `webroot`, gitignored — and are served only through `GET /admin/documentos/{id}/arquivo` (permission `respostas_formularios`; there is no separate "documentos" permission any more). Never put them in `webroot/uploads` (public URLs). Files of forms never submitted are deleted 30 days after the activity starts (`UserDocumentsTable::limparNaoEnviados`, in the lazy-cron).
- **Correção / cancelamento by the organization** (Respostas tab, permission `respostas_formularios`, `RespostasController::pedirCorrecao`/`desfazerCorrecao`/`cancelar`): a correction (`form_corrections`, open while `resolved_at` is null) keeps the vacancy and reopens the form until the correction's own deadline (≤ activity start); still open past that deadline → "Recusada" (`disqualification_reason = correcao_nao_feita`, in `PrazoFormularioService`'s sweep, which the Respostas tab also triggers). There is no "Correção atrasada" status any more (user decision 2026-11-19). Cancelling sets `disqualification_reason = cancelada_organizacao` (+ `disqualified_by`, `disqualification_note` = the motive the person reads); camp vacancy goes to "Chamar próximo" (couple leaves together), event vacancy returns. Both reasons are `MOTIVOS_DEFINITIVOS`: a re-raffle keeps them out (`SorteioService::zerarResultado`).
- **Registro de alterações** (`user_change_logs`, `UserChangeLogsTable::registrar`): ficha edits, Meu cadastro, senha (never the value), permissions, correção/cancelamento/recusa. Shown on the ficha (10 latest + "Ver tudo"); "Conta criada." is synthesized from `users.created`.
- **Soft delete**: most tables have a `deleted` column; queries must filter `deleted IS NULL` (including on joined `Users`) — this has caused leaks before.

### Backend pitfalls that have bitten this project

- **Never hardcode lookup-table ids** (`selection_methods`, `marital_statuses`, `categories`): seed order has changed more than once. Look them up by `title`/name (see `getRaffleMethodId()`, `getCasadoMaritalStatusId()`).
- Once a query has `contain()`, qualify columns in `where()` with the table name (`'PreRegistrations.id' => ...`) or MySQL throws ambiguous-`id` errors.
- Response envelopes are inconsistent across endpoints (`data` vs `activity` vs `categories` …). When a screen "loads empty" with no error, check the real response shape before suspecting the DB.
- After a migration, if a new column silently "doesn't save" in dev, clear `tmp/cache/models` (Cake caches table schema for a long time).
- Migrations must run on MySQL (old ones use `enum`; SQLite is not supported). A fresh DB = `migrations migrate` + `migrations seed`; seeds cover lookup tables, 8 sectors, the admin user and the real FAC/Juvenil forms (`FormulariosSeed`), not test data.

## Frontend architecture

- `src/lib/api.ts` — `apiFetch(endpoint, opts)`: prefixes `VITE_API_URL`, adds the Bearer token from `localStorage`, and on 401 clears the token and redirects to `/login?redirect=…` (pass `redirectOnUnauthorized: false` for public screens).
- `src/lib/stores/auth.svelte.ts` — runes-based `auth` store (`auth.user`, incl. `permissoes`). Only a 401 should drop the saved token.
- `src/lib/services/*Service.ts` — thin per-domain wrappers over `apiFetch`; types in `src/lib/types/models.ts`.
- Routes: `/dashboard/**` is the participant area and is **public** (visitors can browse activities; subscribing goes to login via `src/lib/redirect.ts`); `/admin/**` is the panel ("Painel da Comunidade").
- **Panel permissions are mirrored** in `src/lib/permissoes.ts` (`MENU_DO_PAINEL`, `TELA_POR_CAMINHO`) + `routes/admin/+layout.svelte`. Requirement: a limited user must not notice restrictions — the menu shows only allowed screens and a blocked URL silently redirects to the first allowed one; 403 messages are neutral. Adding a panel screen means updating `PermissoesService::TELAS`, `permissoes.ts`, and the backend `requirePermissao` calls together.
- Business rules shown in the UI are partial mirrors; the backend is always the real gate.
- **Página da atividade** (`dashboard/atividades/[id]`, handoff `Desing/pagina-atividade-handoff`): bloco "Sua inscrição" (one state per situation), timeline cronograma, Valores/Documentos, "Confirmar inscrição" dialog. Eligibility comes from `GET /activities/{id}/elegibilidade` (codes `ja_campista`, `nao_pode_servir`, `nunca_campista`, …, from `InscricoesController::checkAcampamentoEligibility`); `/me/inscricoes` items carry `motivoEm`, `prazoCorrecao`, `perdeuPor`, `pagoEm`, `naoSorteado` (camp "Inscrito" after its raffle was done — no real "Não sorteado" status exists). Camp timeline dates: campista inscrição = `activities.participant_registration_*` (the camping `camper_registration_*` "matrícula" fields are legacy and not shown). Subscribe checks the window on the server too (`InscricoesController::foraDoPeriodoDeInscricao`: campista = activity dates, servo = `raffle_servant_subscription_*`, no end date = not open; event = start date and end/start), so `criarAcampamento` defaults to a window open today. No payment link anywhere (see Pagamento manual): the page shows "Pague {valor} diretamente com a organização…" and "Pago em {data}"; `/me/inscricoes` items carry `pagamento` (valor, prazo, precisaPagar, situacao). Activities show dates without hours (camps too); "Sobre o evento"/"Sobre o acampamento" (`activities.description`, API `sobre`); events show "Idade". Camp timeline: "Sorteio (data prevista)" and one item "Prazo do formulário e do pagamento"; "Vagas" = the raffle vacancies. "Não sorteado" stays computed (user decision 2026-11-20).
- **Fase da atividade** (handoff `Desing/design_handoff_cartao_situacao`): one function `faseDaAtividade` in `lib/faseAtividade.ts` + `SeloFase.svelte` drive the Início card badge, the activity page header and the "Situação" column of Gestão de Atividades (Em breve / Inscrições abertas / Aguardando sorteio / Inscrições encerradas / Acontecendo agora; "Encerrado" = already ended). Computed on the client from the dates in the activity payload (+ `sorteioCampistasRealizado`: "Aguardando sorteio" lasts until the raffle is done, whatever the predicted date); the server's `status` field is no longer used for this. The Início hides activities whose last day has passed (they stay in the panel as "Realizada") and sorts by creation date, newest first (`criadoEm`; user decision 2026-11-21, overriding the handoff's "nearest start").
- **Gestão de Atividades** (`admin/atividades`, handoff `Desing/design_handoff_gestao_atividades`): groups by phase (`faseDaAtividade`, "encerrado" shown as "Realizadas", collapsed), search/filter on the client, order number per group (no DB id), actions shown only with permission. Row numbers come from `GET /admin/atividades/resumo` (permission `atividades`; `inscritos` = active inscriptions, `pagamento` null = nothing to charge, else `noPrazo`/`vencido` using `PagamentoService::precisaPagar`). Deleting an activity with active inscriptions requires `confirmacao` = its name (case/accent/space-insensitive) in the `DELETE` body (`ActivitiesController::delete`, code `confirmar_nome`).
- **Inscritos e sorteio** (`admin/inscricoes/[activityId]`, handoff `Desing/design_handoff_inscritos_sorteio`): page + components in `lib/components/painel/inscritos/` (`AbaInscritos`, `SorteioCampistas`, `SorteioServos`, `JanelaIndicar`), rules/texts in `lib/inscritos.ts`, styles `lib/styles/inscritos.css` (`ins-` prefix, on top of `formularios.css`). Camp: tabs Inscritos / Sorteio de campistas / Sorteio de servos; event: list only. Raffle vacancies are **read-only** here — `POST /sorteio/campistas` ignores the body and uses the camping's `raffle_*_vacancies` (Casado = number of couples). **Re-raffle and reset are refused** (`codigo: sorteio_bloqueado`, `SorteioService::bloqueioDoSorteio`) once anyone drawn or in the queue sent the form or has a payment (payment can be early). `GET /sorteio` also sends `feito_em`, `previsto`, `vagas`, `concorrem`, `nao_concorrem` (city), `bloqueio`, and per sector `vagas_total`/`na_equipe`; `/subscriptions` items carry `conjuge`, `setor`, `cidade`/`daArea`, `formularioEnviado`, `chamadoEm`, `saiuEm`; `chamar-proximo` returns the new `prazo`. Couples are one unit in the raffle lists (`unidades()`). No `confirm()`/`alert()` left.
- **Equipes de Servos** (`admin/equipes`, handoff `Desing/design_handoff_equipes_servos`): one screen replacing "Setores de Servos" (`/admin/setores` now redirects to `?aba=modelo`) and the old team page. Tab "Equipes dos acampamentos" (permission `equipes`, `?atividade={id}`) and tab "Modelo por categoria" (permission `setores`, grid sectors × categories); with only one permission, no tabs. Components in `lib/components/painel/equipes/` (`EquipeAcampamento` is shared with the participant page `dashboard/equipes/[activityId]`, prop `noSite`), rules/texts in `lib/equipes.ts`, styles `lib/styles/equipes.css` (`eq-` prefix). `GET /activities/{id}/sectors` returns `banco` (servo inscriptions with no sector and not servo geral; quitters/disqualified out; masked CPF `***.445.123-**` only with permission `equipes`), `sorteio`, `meu_papel.so_minha_equipe`; a common servo gets only their own sector and no banco, a non-member 403. "Mover" is one server action (`…/members/{userId}/mover`), leadership is `PATCH …/members/{userId}`, `POST /activities/{id}/sectors/aplicar-modelo` only before the servant raffle. **Model sectors enter a camp only on creation or when its category changes** (`ligarSetoresDoModelo`), so a removed sector doesn't come back on edit. A leader removes only non-leaders of their own sector. Sectors are grouped by `place` (Interno/Externo).
- **Forms (Formulários)**: a form is either a camp form (`questions.category_id` + `subscription_type` Campista/Servo) or an event form (`event_forms`, `questions.event_form_id`, type "Participante"; `activities.event_form_id` picks it, null = event subscription concludes immediately). Backend helpers in `FormulariosService` (`formularioDa`, `condicoes`, `copiar`); frontend uses `AlvoFormulario` (`lib/formularios.ts`). Editor and Respostas tab are components (`lib/components/painel/EditorFormulario.svelte`, `RespostasFormulario.svelte`) mounted by thin routes `admin/formularios/[categoria]/[tipo]` and `admin/formularios/evento/[id]`. Event with form: subscription stays "Inscrição em andamento" until the form is sent; the vacancy is only taken on send (row lock `FOR UPDATE`); deadline = `participant_registration_end_date` ?? event start.
- **Meu cadastro** (`/dashboard/perfil`, password at `/dashboard/perfil/senha`): the person edits their own data via `PATCH /users/me` and `POST /users/me/senha` (`UsersController::atualizarMe`/`trocarSenha`). CPF (login) and birth date (decides the camp category) are deliberately read-only there — only the organization corrects them. Participant-area pages share the header `lib/components/CabecalhoSite.svelte`.
- Camps use `src/lib/components/AcampamentoForm.svelte` (Criar/Editar Acampamento, handoff `design_handoff_painel_acampamento`, same pattern as the event screen): tabs "O acampamento" / "Campistas" / "Servos", each track with its own window, predicted raffle date and **one deadline for form and payment** (the server copies `camper_form_deadline` → `participant_payment_date`, `servant_form_deadline` → `servant_payment_date`). Dates without hour like events; order enforced on both sides (`ActivitiesController::validarAcampamento`): opening ≤ closing < raffle < first day, raffle ≤ deadline ≤ first day. Vacancies are only the raffle ones: **Casais has only couples, every other category only men and women** (a married person outside Casais is drawn as man/woman — `SorteioService::categoriaDeCasais`; Casais refuses single campers, code `casais_so_casados`); `total_vacancies` = men + women + 2 × couples (`normalizarAcampamento`). Indicações have no limit and are outside these numbers. Year comes from the first day; idade/matrícula/confirmação/link fields are gone. Sector vacancies are read-only here (template from Setores de Servos, per-camp in the equipes page); `GET /admin/acampamentos/apoio` tells which category forms exist and lists the sectors. Edit accepts `remove_image`, `camping[remove_notice]`, `camping[remove_term]`. Events use `src/lib/components/EventoForm.svelte` (Criar/Editar Evento, handoff `design_handoff_painel_evento`): 3 tabs, save from any tab, all tabs validated on save, card preview. **Event dates have no hour**: first day and opening go at 00h00, closing and payment deadline at 23h59, `duration_days` = last − first + 1; opening and closing are required and closing ≤ first day. The server repeats these rules (`ActivitiesController::validarEvento`, errors keyed by column). Optional age range (`min_age`/`max_age`) **refuses** subscriptions outside it, age counted on the event's first day (`InscricoesController::foraDaFaixaEtaria`, eligibility code `fora_faixa_etaria`). Edit loads from `GET /activities/{id}/edit` (+ `resumo` counts) and saves with `_method=PATCH` (`remove_image=1` drops the cover).
- Visual identity: ivory background, stained-glass blue `#1B2F5E`, gold `#B69E55`, red `#9B2C2C`, Cormorant Garamond + Source Sans 3. Login/register use `AcessoLayout.svelte` + `lib/styles/acesso.css` (`ac-` prefix); older admin screens use `lib/styles/admin-form.css`. Desktop only for now.

### Svelte 5 / TS gotchas

- `$derived(x && x.prop)` or a ternary on a nullable makes svelte-check infer `never`; use `$derived.by(() => { if (!x) return fallback; return x.prop; })`.
- `$page.params.id` is typed `string | undefined`; cast at read time (`$page.params.id as string`).

## Domain glossary (quick)

- **Campista** = camper; **Servo** = volunteer/servant. Categories chain Mirim → FAC → Juvenil → Sênior, plus independent Casais and Discipulados. One can be Campista in a category only once; Servo requires prior Campista in that category or a lower one. These rules apply only to Acampamentos, not Eventos.
- **Sorteio** = raffle (titulares + suplentes). **Indicação** (Base/Forania/Conselho) = manual pick that survives re-raffles and exceeds the quota. Couples are drawn/disqualified as a unit. Only residents of Primavera do Leste/Poxoréu are drawn (`SorteioService::moraNaArea`, free-text city compared without case/accents); **indicação works for any city** and the subscribe dialog doesn't warn about the area (user decision 2026-11-22). The address is only **city + CEP** (street/number/neighborhood were dropped everywhere); it is asked in the "Confirmar inscrição" dialog the first time and edited in Meu cadastro / ficha. It can't be a form question: the raffle needs it before the form opens.
- **Prazo** = deadline. Missing the form or payment deadline frees the slot; an admin clicks "Chamar próximo" to promote the next suplente (no automatic promotion).
- `pre_registrations` = a subscription; `activities` is the base record, with `campings` or `events` holding type-specific fields; sectors: `sectors` → `categories_sectors` (template vacancies) → `activities_categories_sectors` (per edition) → `activities_categories_sectors_users` (team members, `is_coordinator`, `is_substitute`, `is_indicated`).

## Working conventions

- Commit/push only when the user asks; commit messages in Portuguese explaining the *why*.
- Browser testing: log in via `/login` (seed admin CPF `00000000000`; test users use `senha123`), name test data "TESTE CLAUDE …", and delete it (and any files uploaded to `backend/webroot/uploads/`) afterwards.
